I told it no.

That was the first thing I did when uv was suggested to me. Not “let me look into it.” Just no.

The Story #

Why pip? #

Because what else was there.

I was twelve. It was 2012. My first command was pip install requests — not pip3. That one missing character dates me more than anything else I could tell you. Back then, plain pip meant Python 2, and nobody had to specify.

pip came with Python. That was reason enough. I did not choose it any more than I chose the alphabet.

The thing I hated before I needed it #

I did not know requirements.txt existed. When I found out, it shook me.

Then I hated it.

Some of that is just how I’m built. I hate configs. And I have the worse problem too — the moment I know something is configurable, I have to go all the way in. So the safest move was to never learn. Same story with virtual environments. I resented setting them up until the day I stopped noticing I was doing it.

But if I’m being honest, that wasn’t the real reason I gave in.

I gave in because I was tired of running a file and being told the thing it needed wasn’t there. Over and over. requirements.txt fixed that, and I only learned the word “reproducibility” later, after the fact, as a justification for something laziness had already decided.

That is the whole pattern, and it repeats. I don’t adopt tools because they’re correct. I adopt them when staying lazy gets harder than switching.

How I found uv #

Claude told me to install it. I said no.

There wasn’t a reason. I was starting a project and did not want a new tool in the middle of it. Then a moment later I thought, why not, and installed it anyway. That is the entire origin story.

Setup gave me a little trouble. Not the commands — those were fine. What bothered me was pyproject.toml sitting there in the project root. I like things organised. Dangling config files in a root directory make me itch, and now there was another one.

Which, if you’re keeping score, is the third time I resisted a tool for reasons that had nothing to do with whether it worked.

It’s fine now. I stopped seeing the file.

Why I resisted #

The hype didn’t bother me much. Sometimes things are hyped and good. Sometimes they’re hyped and hollow. You can’t tell from the noise, so I don’t read much into it either way.

What scared me was that uv was new.

When I commit to something, I commit. I go deep or I don’t go at all. So the question was never “will this break my project.” It was “am I about to pour myself into a tool that won’t be here in a year.” That’s an expensive mistake for someone who can’t do things halfway.

New tools ask you to spend before you know. I did not want to spend.

Why I love it now #

Three things turned me, and they arrived in order.

First, I cloned a project and it just came up. One command. No venv to create, no install step, no fiddling. The gap between having the code and running the code closed to nothing.

Second, I watched uv add install a package, record it, and update the lockfile in one move. Three things I used to do by hand, in sequence, and forget one of. I had been the glue between those steps for a decade without noticing I was doing a job.

Third — and this is the one that actually mattered — I stopped thinking about environments. I didn’t decide to. I noticed it later, the way you notice a noise only after it stops.

That’s the atomicity I was after. Not speed. I never cared much about speed. I wanted one thing to be responsible for the whole state of my project, so I could stop holding it together myself.

The pattern #

Write it out and it’s embarrassing.

I resisted requirements.txt because I didn’t want to learn a config. I resisted virtual environments because they were tedious. I resisted uv because a file looked wrong in my project root, and because I was afraid to spend myself on something unproven.

Not one of those was a technical objection. Not one.

And every time, the tool won the same way. Not by convincing me. By making the lazy path and the correct path the same path. I was tired of ModuleNotFoundError, so requirements.txt won. I was tired of being the glue between three commands, so uv won.

I’m not a careful engineer who evaluates tools on merit. I’m a lazy one who eventually gets tired enough. The tools that have stuck are the ones that were patient with that.

Coming from pip: the two doors into uv #

Most migration guides tell you to put uv in front of your pip commands. That works. It is also the least interesting thing uv does, and it hid the real tool from me for about two months.

uv has two separate interfaces. They look similar and they are not the same. uv pip operates directly on an environment, the way pip always did. The project commands — uv add, uv sync, uv run — operate on a project, defined by a pyproject.toml. One is a faster pip. The other replaces the whole habit.

I took the first door because it cost nothing. I stayed there too long. This section walks both, in order, and says what each one costs.

Door One: uv as a faster pip #

The mapping is almost boring. That is the point.

pip / pip-tools / virtualenv uv
python -m venv .venv uv venv
pip install requests uv pip install requests
pip install -r requirements.txt uv pip install -r requirements.txt
pip freeze > requirements.txt uv pip freeze > requirements.txt
pip-compile requirements.in uv pip compile requirements.in -o requirements.txt
pip-sync requirements.txt uv pip sync requirements.txt

Same verbs, same flags, new engine underneath.

Install uv once. It does not need Python to run, which is the first sign it is not a normal Python tool:

$ curl -LsSf https://astral.sh/uv/install.sh | sh

Make an environment:

$ uv venv
Using CPython 3.12.3 interpreter at: /usr/bin/python3.12
Creating virtual environment at: .venv
Activate with: source .venv/bin/activate

uv tells you which interpreter it picked. pip’s venv never did. Small thing, saves real time later.

Install something:

$ uv pip install requests
Resolved 5 packages in 12ms
Installed 5 packages in 45ms
 + certifi==2024.7.4
 + charset-normalizer==3.3.2
 + idna==3.7
 + requests==2.32.3
 + urllib3==2.2.2

Look at the two numbers on those first lines. Resolve and install are separate steps, and uv reports them separately. Resolving is the hard part — working out which versions of which packages can coexist. pip does this too, it just never showed you, and it was never fast enough to be worth showing.

That split matters for an intuition you will need later: the expensive thinking and the cheap copying are different operations, and uv is built to do the thinking once and reuse it.

What Door One quietly gives up #

This is where most posts stop. It shouldn’t be.

Your pip config stops being read. uv deliberately ignores pip.conf and PIP_* environment variables. It does not want bug-for-bug compatibility with pip, so it keeps its own configuration hierarchy instead. If your team pipes installs through a private index configured in pip.conf, that setting silently does nothing under uv pip. You configure it again, in uv’s own config.

Not every pip flag exists. uv supports a large subset of pip’s options and subcommands, not all of them. Missing pieces get prioritized by user demand. Common workflows are fine. The further you get from common workflows, the more likely you are to hit a difference.

And the deeper cost: nothing structural changed. You still have a requirements.txt that you maintain by hand. You still have to remember to activate the venv. You still get “works on my machine,” just faster. Door One buys you speed and nothing else.

I ran like this for weeks and told people I had switched to uv. I hadn’t.

Door Two: the project model #

The shift is in what your project’s source of truth is.

Under pip, requirements.txt is a flat list of packages, and it tries to do two jobs at once: declare what you depend on, and pin exactly what got installed. Those jobs conflict. Loosen the pins and builds drift. Tighten them and you can never tell which packages you actually asked for versus which came along as baggage.

uv splits them into two files:

  • pyproject.toml — what you want. Your direct dependencies, loosely constrained. Human-written.
  • uv.lock — what you got. Every package in the tree, exact versions. Machine-written, never edited by hand.

The lockfile is what replaces requirements.txt. pyproject.toml replaces the part of your brain that was trying to remember why urllib3 was in the file.

Bringing an existing project across takes two commands.

$ uv init --bare
$ uv add -r requirements.txt
Resolved 5 packages in 8ms
Installed 5 packages in 40ms

--bare creates just the pyproject.toml — no sample code, no README you did not ask for.

One behaviour to expect: uv add strips the pins on the way in. requests==2.31.0 in your old file becomes plain requests in pyproject.toml, and the exact version gets captured in uv.lock instead. That looks like data loss the first time you see it. It isn’t. It is the split doing its job — the constraint lives in one file, the pin lives in the other. If you genuinely need a hard pin declared, pass it explicitly: uv add 'requests==2.31.0'.

Dev-only packages come in through their own door and land in a separate group:

$ uv add --dev -r requirements-dev.txt

Then three commands cover most days:

$ uv add pandas        # install, record in pyproject.toml, re-lock
$ uv remove pandas     # uninstall, un-record, re-lock
$ uv run app.py        # sync the environment, then run

Each of those is one command doing what used to be three, and the third one is the one that changed my habits. Before every uv run, uv checks that the lockfile matches pyproject.toml and that the environment matches the lockfile. I stopped activating virtual environments. Not out of discipline — I just stopped needing to.

Anatomy of a pyproject.toml #

Worth reading field by field, because you will hand-edit this file eventually.

[project]
name = "my-project"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.32.3",
    "pandas>=2.2.0",
]

[dependency-groups]
dev = [
    "pytest>=8.0.0",
    "ruff>=0.5.0",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

requires-python declares the versions your project supports. It is a range, and it is the constraint uv resolves against.

dependencies is your direct dependency list. Only what you import. Nothing transitive.

[dependency-groups] holds things you need to develop but not to run. The distinction from optional-dependencies matters if you publish: optional-dependencies become part of your package’s public metadata, while dependency-groups stay local to your working copy and are invisible to people who install your package. Test runners, linters, and type checkers go here.

[build-system] only matters if you are packaging a library for others to install. Building an application? You can leave it out.

The lockfile, and the tradeoff it creates #

uv.lock is the reason reproducibility works. It is also the sharpest edge in the tool.

Commit it. Then everyone who clones your repo resolves to identical versions.

Know that it auto-relocks. In development, uv notices a stale lockfile and quietly re-resolves it for you. Convenient at your desk. In CI, that silent update defeats the entire point of having a lockfile. Two flags exist for this:

$ uv sync --locked    # fail the build if uv.lock is out of date
$ uv sync --frozen    # install uv.lock as-is, skip checking pyproject.toml

--locked asserts the lockfile is current. --frozen asserts nothing and just installs what’s there. Use --locked when you want drift to break the build.

And the real tradeoff: uv.lock is not a portable format. The format is specific to uv, which is what lets it support features requirements.txt cannot express. Anything downstream that expects a requirements file — an old Docker base image, a deploy target you do not control, a colleague who has not switched — cannot read it. There is an escape hatch: uv exports the lockfile to requirements.txt, PEP 751’s pylock.toml, or a CycloneDX SBOM.

$ uv export --format requirements-txt --no-dev > requirements.txt

The bridge back out. Useful in Docker builds, and useful the week you have to prove to someone that nothing is locked in.

One more sharp edge. Hand-editing a dependency in pyproject.toml does not update uv.lock. uv detects the mismatch and refuses to run, and the error message is not always obvious about why. Early users hit this hard enough to file it as a footgun. The habit that fixes it: after any manual edit to pyproject.toml, run uv lock. uv add and uv remove do it for you.

Layer Three: Python versions and tools #

This is the part with no pip equivalent at all, and it is where “uv replaced five tools” stops being marketing.

Python versions — what pyenv did:

$ uv python install 3.12
$ uv python pin 3.12
Pinned `.python-version` to `3.12`

uv reads .python-version on every command, searching the working directory and each parent. Commit the file. Your team lands on the same interpreter without anyone being told to.

One constraint to hold in your head: .python-version pins your development interpreter, requires-python in pyproject.toml declares the supported range, and the pin has to satisfy the range. Break that and uv reports an incompatibility rather than guessing. Two files, two jobs — the same split as pyproject.toml and uv.lock.

Global CLI tools — what pipx did:

$ uv tool install ruff
Resolved 1 package in 6ms
Installed 1 package in 2ms
 + ruff==0.5.4
Installed 1 executable: ruff

Or skip installing entirely. uvx is an alias for uv tool run. It builds a temporary isolated environment, runs the tool, and throws the environment away.

$ uvx pycowsay 'hello uv'
Resolved 1 package in 167ms
Installed 1 package in 9ms
 + pycowsay==0.0.0.2
------------
< hello uv >
------------
 \   ^__^
  \  (oo)\_______
     (__)\       )\/\
         ||----w |
         ||     ||

First run pays for the download. Cached runs come back in tens of milliseconds.

The tradeoff here is isolation, and it bites. A tool run through uvx cannot see your project’s packages. If the tool needs them — pytest and mypy both do — use uv run instead, or it runs against an environment that knows nothing about your code. The rule: does the code belong to your project, or is it a standalone tool? Project code gets uv run. Standalone tools get uvx.

Which door to walk through #

Both, in this order. That is not a hedge, it is a migration path.

Start at Door One if you have a working project and a deadline. uv pip install is a one-line change to your muscle memory and your CI scripts. You get the speed immediately and risk almost nothing. Just know you have changed your installer and nothing else.

Move to Door Two when the thing hurting you is not speed. If your problems sound like “it worked yesterday” or “it works on my machine” or “why is this package even in here” — those are structure problems. A faster installer cannot fix them. The lockfile can.

Stay at Door One in one real case: legacy projects and situations where you need direct manual control over an environment, without a pyproject.toml in the picture. Similarly, a few tools call pip directly — Jupyter’s %pip magic, for one — and those need actual pip present in the environment. The project model assumes your project is the unit of work. When it isn’t, don’t force it.

I went through Door One for the speed and stayed for weeks. Door Two is the one that changed how I work.

Where uv stops being obvious #

Section 2’s tradeoffs were about the tool’s own design. These are about the places uv meets systems it does not control: a container build, a CI runner, a scientific stack held together by C libraries, a repo with eight packages in it.

Two of the three turn out to be configuration problems. One is a wall, and no amount of configuration moves it.

Containers: speed makes layering matter more, not less #

The intuition that trips people up: uv is so fast that Docker layering feels unnecessary. It is the opposite. When installs take 40ms, the download and the layer invalidation become the whole cost. Getting the layer order wrong now dominates your build time in a way it never did with pip, because there is nothing else left to blame.

Split the dependency install from the project install. uv sync --no-install-project installs your dependencies but not your project. Dependencies change rarely; your code changes constantly. Separating them means editing a source file does not re-resolve your dependency tree.

FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app

# Dependencies only — cached until uv.lock changes
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

# Now the project, which changes on every commit
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked

The bind mounts matter: pyproject.toml is needed to identify the project root and name, but the project contents stay out of the image until the final sync.

Three settings you will otherwise discover through warnings:

UV_LINK_MODE=copy — uv hardlinks files by default. A Docker cache mount and your sync target sit on different filesystems, where hardlinks do not work. Without this, uv warns on every build.

.venv in .dockerignore — the project virtual environment depends on your local platform. It should be built fresh inside the image, never copied in.

UV_COMPILE_BYTECODE=1 — precompiles bytecode, which improves startup time at the cost of longer installs and a bigger image. A production tradeoff, not a default. Choose deliberately.

The workspace footgun. In a workspace, that first layered sync has to use --frozen, not --locked. uv cannot verify the lockfile is current without every member’s pyproject.toml, and those have not been copied in yet. Use --no-install-workspace to exclude all members, then --locked on the second sync once everything is present.

And to ship an image without uv in it: --no-editable installs the project in non-editable mode, which drops the dependency on your source directory. That lets a multi-stage build copy just the virtual environment into the final image and leave the source behind.

CI: the cache you should not keep #

This is the most counterintuitive result I found in the whole tool, and it is worth internalizing because it inverts a habit everyone has.

Standard CI advice: cache your dependencies. With uv, it is often faster to leave pre-built wheels out of the cache and re-download them from the registry every run.

Why: restoring a cache is I/O, and uv’s download-plus-install path is fast enough to beat it. The cache stops being a shortcut and becomes overhead. uv ships a command for exactly this — uv cache prune --ci strips pre-built wheels and unzipped source distributions while keeping wheels that had to be built from source, since those are genuinely expensive to reproduce.

Astral recommends running it at the end of the CI job. Worth noting the nuance: at least one third-party action leaves that pruning off by default, citing Charlie Marsh’s own research. The honest read is that the right answer depends on your dependency mix — how much of your tree needs compiling. Measure it rather than copying a config.

A working baseline:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: astral-sh/setup-uv@v8.1.0
        with:
          enable-cache: true
      - run: uv sync --locked --all-extras --dev
      - run: uv run pytest

--locked is the point of this file. It fails the build if uv.lock is out of date, instead of silently re-resolving.

Two sharp edges:

actions/checkout must run before setup-uv. The reverse order is not supported.

The first run on a new cache key prints “No GitHub Actions cache found.” This is expected, not a misconfiguration — the action cannot distinguish a legitimate first run from a broken cache-dependency-glob, so it warns either way.

The wall: conda and native dependencies #

Everything above is tuning. This part is not, and I think it is where the “uv replaces five tools” framing does real damage — because it sets up an expectation the tool cannot meet.

uv installs Python packages from PyPI. That is the entire scope. It cannot install the CUDA toolkit, GDAL, or HDF5. It cannot install compilers, or share an environment with R or Julia.

The reason is structural, not a missing feature. A conda package is not required to be Python at all — it can be a shared library, a compiler, or a command-line tool like ffmpeg. The format is just “a binary for this platform with these dependencies,” and conda’s solver reasons across languages because it knows about non-Python deps. A wheel, however much compiled C it contains, is still shaped around a Python entry point.

The concrete case: a CUDA build of PyTorch needs a specific CUDA runtime. conda installs both together, atomically. With PyPI, you install CUDA system-wide yourself and hope the wheel matches.

There is also no import path. Unlike conda-to-pixi, uv has no --import flag for environment.yml, because uv reads PyPI and conda reads channels. Migration means re-declaring your dependencies by hand.

So the decision is about where your packages live, not which tool is better:

Your dependencies Tool
All on PyPI as wheels — NumPy, pandas, scikit-learn, SciPy uv
Native libs from conda-forge — CUDA, GDAL, HDF5, compilers conda family
Both conda or pixi for the native foundation, uv for the Python layer

These are not competitors. Each is best at a specific kind of dependency.

The interesting middle option is pixi. It resolves conda-forge and PyPI packages together into a single lockfile — and it uses uv internally for the PyPI half. Project environments live in a local .pixi/ directory, with no global conda activate step. If you want uv’s project model but need conda’s package universe, that is the tool, and it is under-mentioned in every uv post I have read.

Two smaller caveats worth knowing, though attribute these loosely — they come from practitioner reports rather than official docs. uv has not shipped a 1.0, which some corporate procurement processes gate on. Its offline behaviour is reportedly not fully mature, which matters in air-gapped networks. And the cache grows: one user reported over 20GB after a year, clearable instantly with uv cache clean, but worth watching on disk-constrained runners.

Workspaces: one lockfile, one Python, shared blame #

uv borrows workspaces from Cargo: a collection of packages managed together, each with its own pyproject.toml, all sharing a single lockfile.

[project]
name = "albatross"
dependencies = ["bird-feeder", "tqdm>=4,<5"]

[tool.uv.sources]
bird-feeder = { workspace = true }

[tool.uv.workspace]
members = ["packages/*"]
exclude = ["packages/seeds"]

workspace = true tells uv to resolve bird-feeder from the workspace instead of PyPI.

uv lock operates on the whole workspace at once. uv run and uv sync default to the root, and both take --package to target a member from any directory.

The shared lockfile is the feature. Every package in the repo resolves against one consistent set of versions. It is also the source of all three tradeoffs.

One requires-python for everyone. uv enforces a single Python requirement across the workspace — the intersection of every member’s requires-python. If you need to test one member on a Python version the rest of the workspace does not support, you fall back to uv pip in a separate virtual environment. The shared lockfile cannot express two answers.

Conflicting requirements break the model. Workspaces are not suited to members with conflicting dependencies, or members that each want their own virtual environment. The alternative is path dependencies — declare each package independently and point at it with tool.uv.sources. You keep most of the benefit and lose uv run --package; commands must then run from the relevant directory.

And uv cannot enforce the boundaries it helps you draw. Python provides no dependency isolation, so uv cannot stop one workspace member from importing a dependency declared by another. Your package boundaries are a convention the tool records but cannot police. An accidental cross-import works fine locally and fails the day you publish the package alone.

When it earns its keep: a root application with accompanying libraries, a library with a performance-critical extension module in Rust or C++, or a plugin system where each plugin depends on the root. uv itself is built this way — core library and CLI as separate packages, so each can be tested without the other.

The shape of it #

Three areas, three different kinds of limit.

Containers and CI are configuration problems. They have right answers, the right answers are non-obvious, and you find them by reading docs rather than by intuition. The CI cache result in particular inverts standard practice.

Workspaces are a design problem. One lockfile buys consistency and costs flexibility. That trade is inherent, not a bug, and if your packages genuinely disagree about their dependencies you should not be in a workspace.

conda is a scope problem, and the only one where the answer is “use something else.” uv is a Python package manager that got very good at being a Python package manager. It did not become a system package manager, and it is not trying to.

None of this argues against uv. It argues against the framing that one binary replaced everything — which was the thing that made me suspicious of uv in the first place, and turned out to be the only part of my skepticism that held up.
